## 3. ADR à créer

### ADR-0022 — Formalisation `@include` (Gap-16, P2)

**Décision** : introduire une grammaire canonique pour les directives `@include` dans les fichiers d'entry-point (AGENTS.md, CLAUDE.md, SYSTEM.md). Format :

```
@include <path-relative-to-file>
@include <path> [optional <description>]
```

Un outil `tools/vbb-include-lint.py` parse les fichiers entry-point et valide :
- Chaque `@include` cible un fichier existant
- Le fichier cible est canonique (pas de `@generated` cyclique)
- Le graphe d'inclusion est acyclique

**Justification** : aujourd'hui, `@AGENTS.md`, `@SYSTEM.md`, `@docs/PILOTAGE.md` sont des directives silencieuses. Un fichier renommé casse les liens sans détection.

### ADR-0023 — Sentinel `@generated` + détection (Gap-17, P2)

**Décision** : introduire un sentinel canonique `@generated by <tool-name> at <YYYY-MM-DD>` en tête des fichiers générés. Un outil `tools/vbb-generated-check.py` valide :
- Présence du sentinel sur les fichiers marqués générés (RELATIONS.md, AGENTS.md, etc.)
- Si le sentinel est absent OU si le contenu dérive de la source canonique → warning

**Justification** : sans sentinel, un humain peut éditer `RELATIONS.md` à la main et le drift n'est détecté qu'à la prochaine régénération.

### ADR-0024 — Snapshot→log cumulatif (Gap-18, P2)

**Décision** : étendre `t-vbb-impact-analyzer` avec un mode `--project-to-log` qui projette les findings d'un snapshot vers `docs/IMPACT_LOG.md` (cf. ADR-0010). Chaque finding devient une entrée `breaking`/`additive`/`deprecation`/`fix`/`consumed_change` selon heuristique.

**Justification** : aujourd'hui, les snapshots sont isolés. Avec `IMPACT_LOG.md` cumulatif (ADR-0010), il faut un mécanisme pour les alimenter depuis l'existant.

# ADR — 0012-codegen-agents-claudemd

**Status**: ACCEPTED  
**Date**: 2026-07-13  
**Route**: STRUCTUREE  
**Décideurs**: Brice Sodini (project lead & canon owner)  
**Liée à**: docs/strategy/vbb-evolution-multi-service-support/01_GAP_ANALYSIS.md § Gap-03  
**Liée à POC**: vide

## Contexte

Vibebackbone maintient plusieurs fichiers « entrée-projet » qui doivent rester synchronisés avec le canon : `AGENTS.md` (racine), `distributions/claude/CLAUDE.md`, `distributions/pi/SYSTEM.md`. Ces fichiers contiennent les Critical Rules 1-13 + des directives d'inclusion (`@AGENTS.md`, `@SYSTEM.md`).

Aujourd'hui, le pattern codegen existe pour `ARCHITECTURE.md → RELATIONS.md` (cf. `tools/vbb-architecture.py`, fonction `graph --write`, `RELATIONS_PATH = Path("docs/RELATIONS.md")`). Mais aucun mécanisme équivalent n'existe pour `AGENTS.md` / `CLAUDE.md`. Ces fichiers sont écrits à la main.

Conséquence : si Brice modifie une Critical Rule dans `docs/PILOTAGE.md` ou `docs/CONVENTIONS.md`, il doit reporter manuellement dans 3+ fichiers (`AGENTS.md`, `distributions/claude/CLAUDE.md`, `distributions/pi/SYSTEM.md`). Drift silencieux possible — d'autant que `load_policy: always` (cf. `PILOTAGE.md` ligne 3, `SYSTEM.md`, `AGENTS.md`) est une **convention documentaire**, pas un mécanisme enforceable.

## Décision

**Étendre `tools/vbb-architecture.py` pour ajouter un mode `agents --write` qui génère `AGENTS.md` (racine) et `distributions/claude/CLAUDE.md` depuis une source canonique.**

### Source canonique

Le générateur compose à partir de :
- `docs/CONTEXT.md` (frontmatter : nom, description, archetype — cf. ADR-0006)
- `docs/PILOTAGE.md` (Critical Rules 1-13, extraites par sections `## Critical Rules` ou similaires)
- `docs/CONVENTIONS.md` (Pillars 1-5 — référence)
- `docs/AGENTIC_RUN_PROTOCOL.md` (7 phases, P.R2)

### Cible de la génération

| Fichier généré | Contenu |
|----------------|---------|
| `AGENTS.md` (racine) | Header du repo : 13 Critical Rules + lien vers canon + lien vers `distributions/*/SYSTEM.md` |
| `distributions/claude/CLAUDE.md` | Version Claude (adaptée : directives `@AGENTS.md`, `@SYSTEM.md`) |
| `distributions/pi/SYSTEM.md` | Version Pi (déjà partiellement canonique, mise à jour mineure) |

### Mode d'invocation

```bash
python tools/vbb-architecture.py agents --write
# ou
python tools/vbb-architecture.py agents --check   # dry-run, exit 1 si drift détecté
```

Le mode `--check` est destiné au CI pour détecter le drift entre les fichiers générés et la source canonique. Exit 1 si drift, exit 0 si cohérent.

### Idempotence

La génération est **idempotente** : exécuter 2 fois produit le même résultat (modulo timestamps). Les fichiers générés peuvent être **commités en l'état** (ils sont alors stables jusqu'à la prochaine modif canon) OU **gitignored** et regénérés au setup (le choix est documenté dans le README de l'outil).

## Conséquences

### Positives
- Drift entre source canonique et fichiers distribué devient détectable (`--check`).
- Modifier une Critical Rule demande un seul edit (source canonique) + une régénération.
- Les fichiers générés sont traçables (commentaire `<!-- generated by tools/vbb-architecture.py agents -->` en haut).
- Pattern cohérent avec `RELATIONS.md` (déjà généré).

### Négatives / coûts
- Le générateur doit parser le canon (PILOTAGE.md, CONVENTIONS.md, etc.) — code additionnel ~200 lignes.
- Les fichiers générés doivent être commités OU gitignored (choix par projet).
- `--check` en CI ajoute une étape (mais rapide, < 1 seconde).

### Neutres
- Aucun canon modifié.
- `distributions/pi/SYSTEM.md` (qui suit un pattern proche) n'est pas fusionné dans le générateur — il garde sa propre cohérence interne, mais profite du même `--check`.

## Alternatives rejetées (≥ 2)

### Alternative A — Continuer d'éditer les fichiers à la main
- **Description** : statu quo. Brice reporte manuellement chaque Critical Rule dans 3+ fichiers.
- **Pourquoi rejetée** : source d'erreurs humaines, drift silencieux.

### Alternative B — Un seul fichier `AGENTS.md` racine, tous les outils le lisent
- **Description** : supprimer les variantes `distributions/claude/CLAUDE.md` et `distributions/pi/SYSTEM.md` ; tout le monde lit `AGENTS.md` racine.
- **Pourquoi rejetée** : les distributions ont des besoins spécifiques (Claude veut `@AGENTS.md` directives, Pi veut son format `SYSTEM.md`). Garder les variantes mais les générer depuis la source canonique est plus modulaire.

### Alternative C — Pre-commit hook qui vérifie la cohérence
- **Description** : un hook pre-commit rejette les commits si les fichiers générés ne sont pas à jour.
- **Pourquoi rejetée** : bloque les commits mais ne génère pas. L'utilisateur doit régénérer manuellement. La régénération automatique est plus confortable.

## Risques

| Risque | Probabilité | Impact | Mitigation |
|--------|-------------|--------|------------|
| Le générateur produit un fichier différent de la version manuelle (diff inutile) | moyenne | faible | Premier lancement = inspection diff manuelle + ajustement du générateur. Itération suivante = idempotent. |
| Les directives d'inclusion (`@AGENTS.md`, `@SYSTEM.md`) sont perdues dans la génération | moyenne | moyen | Le template du générateur les inclut explicitement (test post-génération). |
| Le générateur devient couplé à la structure du canon (PILOTAGE.md change → générateur casse) | moyenne | moyen | Le générateur parse par sections sémantiques (`## Critical Rules`), pas par regex fragile. Tests = out of scope ce run. |

## Hypothèses

- La structure de `PILOTAGE.md` (sections `## Critical Rules`, etc.) est stable.
- Les fichiers générés peuvent être commités (choix par défaut recommandé).
- Pas d'autres consumers des fichiers générés en dehors des distributions actuelles.

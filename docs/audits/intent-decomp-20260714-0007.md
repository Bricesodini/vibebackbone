## Executive summary

Le plan tient en trois runs indépendants. Le premier corrige la fiabilité de
`vbb-executor.py` sans nouvelle abstraction. Le deuxième réconcilie la vérité
active et compresse les cinq `SKILL.md` les plus lourds à comportement constant.
Le troisième teste une voie minimale pour rafraîchir les projets consommateurs ;
il s'arrête avant implémentation si la solution exige un nouvel outil, un nouveau
skill ou plus de 60 lignes de code produit. Aucun nouveau canon n'est prévu.

## Planning verdict

**ACTIONABLE_WITH_CAVEATS** — RUN 01 et RUN 02 sont directement exécutables.
RUN 03 commence par un POC et peut se conclure par `DEFERRED` si une solution
légère ne suffit pas.

## Non-growth contract

Ces contraintes s'appliquent aux trois runs :

1. **Aucun nouveau skill, outil transversal, format d'artefact ou couche de
   gouvernance.**
2. **Total `SKILL.md` final ≤ 362 069 caractères.**
3. **Chaque skill touché doit rétrécir ou rester stable.** Aucune compensation
   globale ne permet de rendre un skill individuel plus lourd.
4. **Top 5 final ≤ 62 700 caractères** (-15 % minimum) et aucun des cinq ne doit
   rester au-dessus de 13 000 caractères.
5. Les `description:` restent ≤ 500 caractères / 10 lignes et conservent leurs
   déclencheurs utiles.
6. Pas de nouveau document de référence pour déplacer artificiellement le
   poids. Utiliser les références canoniques déjà présentes et supprimer la
   duplication.
7. Hors tests et artefacts de run, le diff global doit être **net négatif en
   caractères**. Toute exception bloque le closeout et revient en décision.

### Compression method

Dans chaque skill, supprimer dans cet ordre :

1. exemples redondants déjà exprimés dans le contrat ou le template ;
2. répétitions entre ROLE, SCOPE, PROCESS et SUPPORT BOUNDARY ;
3. longues explications de motivation qui n'influencent aucune action ;
4. tableaux dont chaque ligne reformule une règle existante ;
5. rappels de protocole déjà couverts par une référence canonique existante.

Ne pas supprimer : blocking conditions, ordre des étapes, artefacts obligatoires,
taxonomie de verdict, règles de preuve, triggers et support boundary utile.

### Distribution impact

La compression est une modification Core générique propagée aux quatre
distributions par le catalogue partagé. Aucun glue provider ne doit changer.
Consigner cette décision en une ligne dans `docs/DISTRIBUTIONS.md` § Decisions
log, sans répéter le plan.

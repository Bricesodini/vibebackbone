# Intent decomposition — consumer managed hook bundle

**Date**: 2026-07-14 12:42 Europe/Paris
**Source**: décision `Go` de Brice, `SEC-CRED-005`, `TER-001`, POC NO-GO
`2026-07-14_0721_consumer-refresh-poc`
**Verdict**: `ACTIONABLE`

## 1. Contexte et résumé exécutif

L'initialiseur traite aujourd'hui tous les fichiers comme des sorties de
bootstrap : skip ou overwrite global. Cette sémantique ne permet ni de mettre à
jour un runtime VBB, ni de préserver une personnalisation avec preuve. Le plan
est actionnable en bornant la solution au bundle runtime du hook ; les documents
de vérité projet restent générés une fois et hors refresh automatique.

## 2. Architecture existante

`tools/vbb-project-init.py` génère des documents projet et copie un redirecteur
obsolète. `scripts/install-vbb-hooks.sh` est l'installateur canonique et dépend de
deux hooks, du credentials gate et du loop-closure gate. Les quatre distributions
consomment le même Core ; aucune déclinaison provider n'est requise.

## 3. Spécification analysée

| Feature | Actor | Flow | Data | Priority |
|---|---|---|---|---|
| Bootstrap hook complet | Mainteneur consommateur | init → copie bundle → installe hooks | assets Core | P1 |
| Refresh sûr | Mainteneur consommateur | init répété → compare hashes → refresh/refus | manifeste de hashes | P1 |
| Erreur fidèle | CI/agent | échec bundle/hook → stderr + exit 1 | diagnostic sans secret | P1 |
| Ownership explicite | Architecte | docs projet séparées des assets gérés | contrat architecture | P1 |

## 4. Non-objectifs

- Explicite : aucune fusion des documents projet, aucun runtime externe, aucun
  refresh universel des templates.
- Inféré : aucune migration automatique des customisations historiques sans
  manifeste ; aucune nouvelle dépendance Python.
